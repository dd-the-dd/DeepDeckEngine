# Data-driven runtime fixture runner

This parser-free binary executes already-compiled canonical IR against a small,
deterministic game state. Adding a card proof changes JSON only; Rust is rebuilt
only when the runner or engine changes.

From the repository root, build the stable runner once:

```powershell
$env:CARGO_TARGET_DIR = '.tmp/targets/card-migration'
cargo build -p deepdeck-runtime-fixture-runner
```

Then run any number of fixtures directly, without invoking Cargo or compiling
Rust again:

```powershell
.\.tmp\targets\card-migration\debug\deepdeck-runtime-fixture-runner.exe `
  crates/deepdeck-runtime-fixture-runner/fixtures/llanowar-elves.json `
  crates/deepdeck-runtime-fixture-runner/fixtures/stock-up.json
```

Every input object uses `deepdeck-runtime-fixture/v1`. Unknown fields and
unsupported schema versions fail before execution. Standard output contains one
compact `deepdeck-runtime-fixture-result/v1` JSON object per fixture; any failed
fixture makes the process exit with code 1.

The runner can execute a generated legal `castSpell` action by source definition.
Set `useAlternativeCost` to select the alternative-cost declaration and
`alternativeExileDefinitionId` to disambiguate the card paid to an `exileCard`
cost. Availability-only fixtures use `spellCastAvailable`; state assertions
include `lifeTotal`, `zoneCount`, `zoneContains`, `manaPoolEquals`, and
`stackDepth`. The engine remains authoritative for legality and payment.

The `activateAbility` action selects a real non-mana activation generated by
the engine. Identify the source by definition, optionally disambiguate its
`abilityRuleIndex`, and provide canonical targets. A
`permanentDefinition` target must resolve to exactly one current battlefield
object; zero or duplicate matches fail explicitly. The resolved target map
must exactly match a legal engine declaration, so fixtures cannot bypass
selector validation, costs, priority, or stack behavior.

Cards may provide a `rules` array when a scenario needs their complete compiled
rule set. When omitted, the fixture-level `rule` remains the backward-compatible
rule attached to action and assertion sources. `resolveTopStack` resolves one
stack object through the normal engine path, which allows a fixture to cast an
opposing spell, cast a counterspell, and verify both resolution destinations.

`runMulligans` executes the engine's opening-hand procedure with optional
`freeMulligans` and `maximumMulligans` limits. Script one `chooseOption` per
player's keep-or-mulligan decision, followed by any opening-hand replacement
choices. This exercises pregame abilities through the same decision and zone
transition boundaries as a normal game setup.

For mana sources with several legal production choices, `activateManaAbility`
and `manaAbilityAvailable` accept `manaSymbols`. The runner selects the real
engine action whose `manaProduced` decision exactly matches that sequence.
Omitting `manaSymbols` remains valid only when the source has one legal choice;
an ambiguous activation is rejected explicitly.

`chooseCardName` scripts persistent name choices without a card-specific test
provider. `activatedAbilityAvailable` can select an exact non-mana rule index
and target map, complementing `manaAbilityAvailable`; together they prove that
generic activation prohibitions preserve mana exceptions.

`permanentPowerToughness` compares the engine's effective power and toughness,
including continuous effects and counters, rather than only the printed or
stored base values. `permanentCounter` compares one named counter and treats an
absent counter as zero. Both assertions require the definition id to identify
exactly one permanent controlled by the named player.

Each fixture player may also declare an initial `graveyard` array. Those cards
are placed through the deterministic engine setup boundary before execution;
they participate in uniqueness validation, source lookup, and zone assertions.

Fixture cards may set `isCommander: true` or `isToken: true`. The runner
preserves those generic card-definition characteristics in every supported
initial zone, allowing mana, casting, replacement, and state-based behavior to
be proved without adding card-specific setup code.

Players may declare `commandZone` alongside `hand`, `library`, `battlefield`,
and `graveyard`. Zone placement and the `isCommander` designation are separate:
a designated commander in the command zone does not satisfy a condition that
counts commanders controlled on the battlefield. The deterministic setup API
preserves those objects without changing the existing position structure.
